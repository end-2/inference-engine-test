# 고유 입력별 캐시 초기화 성능

고유 입력 32개와 128개에 대해 동시성 1, 2, 4, 8의 각 측정 전에 PVC 캐시를 비우는 sweep을 각각 한 번 실행했습니다. 본 요청 800건과 워밍업 16건은 모두 성공했습니다. 출력 길이 부족은 없었으며, 목표보다 사용량이 많은 요청은 24건이었습니다.

## 측정 조건

- 실행일: 2026-09-20 UTC (한국 시간 2026-09-21). [실행 시각과 이미지 ID](run.json).
- 이미지 `local/llama-enhanced-cache:0.1.0`, 모델 Qwen2.5-0.5B-Instruct Q4_K_M.
- 추론 Pod 12 CPU, 16 GiB, AIPerf Pod 1 CPU, 1 GiB. requests와 limits를 같게 설정했습니다.
- RAM 캐시 64 MiB, 디스크 캐시 1,024 MiB, 최소 prefix 32토큰.
- 각 동시성 전에 추론 Pod를 종료하고 shutdown flush가 끝난 뒤, 전용 PVC의 모든 캐시 파일을 삭제했습니다. 빈 PVC를 확인한 후 새 추론 Pod를 시작해 RAM도 초기화했습니다.
- 워밍업 2건 이후 본 측정 100건을 실행했습니다. 각 단계 안에서는 캐시가 채워지고 재사용될 수 있습니다.
- 입력/출력 목표 64/32토큰과 256/64토큰, 설정 비율 각 50%, seed 42, 순차 입력, 스트리밍, `ignore_eos=true`.
- 별도 클라이언트 부하는 생성하지 않았으며, 기존 모니터링 서비스는 실행 상태였습니다.

첫 동시성은 두 조건 모두 빈 캐시에서 시작합니다. 이후 동시성에서는 초기화 조건이 이전 단계의 캐시를 재사용할 수 없습니다. 보존 조건과는 RAM 유지 및 Pod 수명도 달라 PVC만의 효과로 분리하지 않았습니다. 단회 측정이므로 작은 차이를 일반화하지 않습니다.

32개 설정은 본 측정 100건에서 입력 32개를 반복하고, 128개 설정은 단계별로 고유 입력 100개를 사용합니다. 실제 입력/목표 출력 93/32토큰과 285/64토큰의 요청 수는 각각 57/43건과 54/46건으로 보존 조건과 같습니다.

## 출력 길이와 검증 기록

- 고유 입력 128, 동시성 1: 목표 64토큰 요청에서 65토큰 6건.
- 고유 입력 128, 동시성 2: 목표 64토큰 요청에서 65토큰 6건.
- 고유 입력 128, 동시성 4: 목표 64토큰 요청에서 65토큰 6건.
- 고유 입력 128, 동시성 8: 목표 64토큰 요청에서 65토큰 6건.

처리량에는 서버가 보고한 사용량을 그대로 사용했습니다. 출력 길이 초과는 요청 오류와 별도로 기록하며, 해당 조건은 고정 출력 길이 검증을 완전히 통과한 것으로 보지 않습니다. [32개 검증](entries-32/run.json)과 [128개 검증](entries-128/run.json)에 PVC 삭제 결과, 입력 체크섬과 불일치 요청 ID를 저장했습니다.

요약은 [CSV](summary.csv), 각 동시성의 AIPerf 요약은 `entries-*/c*/artifacts/profile_export_aiperf.json`에 저장했습니다. 전체 원본, 요청별 CSV, 자원 시계열과 로그도 같은 결과 폴더에 로컬 보관하며, 대용량 자료는 Git에서 제외합니다. 실행 manifest와 Pod 기록은 각 동시성 폴더에 있습니다.

# Disaggregation의 처리량이 낮은 이유

이 구성에서는 Decode worker를 2개에서 1개로 줄인 영향이 Prefill과 Decode를 겹쳐 실행하는 이득보다 큽니다. 상태 전달 비용도 추가됩니다. OOM으로 중단한 두 번째 반복은 [성능 집계](summary.md)에 포함하지 않았으므로, 아래 차이를 실패한 요청 때문에 낮아진 처리량으로 해석하지 않습니다.

## Decode 처리 용량과 단계 불균형

Aggregation의 두 worker는 각각 Prefill과 Decode를 실행합니다. Disaggregation은 Prefill worker 1개와 Decode worker 1개이며, 각 worker는 batch 1로 한 번에 한 요청을 처리합니다. 물리 GPU 1개의 MPS share 2개를 사용하는 총자원은 같지만 Decode를 동시에 수행하는 worker 수는 다릅니다.

[Worker 단계별 기록](phase-diagnostics.json)의 평균은 다음과 같습니다. 입력은 채팅 템플릿을 포함한 실제 토큰 수입니다. 동시성별 기록을 합친 값이며, 94/256과 734/16에는 같은 길이의 혼합 부하 요청도 포함됩니다.

| 실제 입력/출력 | Prefill ms | Decode ms | Decode / Prefill | 상태 크기 MiB |
| --- | ---: | ---: | ---: | ---: |
| 94/16 | 32.7 | 426.4 | 13.0 | 2.26 |
| 94/256 | 33.1 | 7,185.8 | 217.2 | 2.26 |
| 734/16 | 80.7 | 438.9 | 5.4 | 16.33 |
| 734/256 | 93.3 | 7,221.3 | 77.4 | 16.33 |

가장 긴 입력과 가장 짧은 출력에서도 Decode가 Prefill보다 5.4배 오래 걸립니다. 입력 734, 출력 256에서는 두 계산 시간 합계 중 Prefill 비중이 약 1.3%입니다. 따라서 분리해서 숨길 수 있는 Prefill 시간은 작고, Decode worker 하나가 계속 병목으로 남습니다.

출력 256토큰을 약 7.22초에 생성하는 Decode worker 하나의 처리량은 약 35.5 tok/s입니다. 실제 동시성 8에서 Disaggregation은 35.25 tok/s로 이에 가깝습니다. Aggregation은 두 worker가 생성하므로 66.46 tok/s를 기록했습니다. 전체 10개 workload의 동시성 8에서 D/A 처리량은 0.53~0.57입니다.

MPS client별 active thread 한도는 50%였습니다. 이는 독립 GPU 두 개나 정확한 연산 성능의 절반을 보장하는 분할이 아닙니다. Prefill client가 쉬어도 Decode client의 설정된 active thread 한도가 자동으로 100%가 되지 않습니다. 따라서 이 균등 분할이 현재 부하의 역할별 계산 비중과 맞지 않습니다. 한도의 동작은 [NVIDIA MPS 문서](https://docs.nvidia.com/deploy/mps/when-to-use-mps.html)를 참고합니다.

## 대기열이 TTFT를 키운다

첫 출력 토큰도 Decode worker에서 선택합니다. 앞 요청의 긴 Decode가 끝날 때까지 다음 요청은 첫 토큰을 받지 못합니다.

| 합성 입력/출력, 동시성 | A tok/s | D tok/s | A TTFT ms | D TTFT ms |
| --- | ---: | ---: | ---: | ---: |
| 64/16, 1 | 33.64 | 33.30 | 89.3 | 104.2 |
| 704/16, 1 | 31.01 | 26.67 | 136.8 | 230.6 |
| 704/256, 8 | 66.46 | 35.25 | 20,002.1 | 44,594.9 |
| 혼합, 8 | 63.19 | 35.50 | 11,985.3 | 26,299.7 |

실제 입력 734, 출력 256의 Disaggregation worker 로그 128개를 동시성 1, 2, 4, 8에 걸쳐 평균하면 Prefill 대기는 30.6ms, Decode 대기는 17,808.9ms입니다. 같은 조건들의 Aggregation worker 대기는 6,764.5ms였습니다. Aggregation에서는 전체 추론 전 대기를 `prefill_queue_ms`로 기록합니다. 이 평균은 특정 동시성의 TTFT와 직접 더하는 수치가 아니라 대기가 어느 단계에 쌓였는지 보여주는 진단값입니다.

## KV 상태 전달의 추가 비용

상태는 Prefill GPU에서 CPU로 복사되고, HTTP로 Prefill→Router→Decode를 거쳐 다시 GPU로 복사됩니다. 실제 입력 734토큰에서는 요청당 약 16.33 MiB를 두 HTTP 구간에서 전달합니다. 로그의 export는 약 31ms, import는 약 9ms입니다. 입력 94토큰에서는 각각 약 3.4ms와 4.5ms였습니다.

동시성 1, 출력 16에서 분리 구성의 TTFT 증가는 짧은 입력에서 약 15ms, 긴 입력에서 약 94ms입니다. 상태 전달과 직렬화가 추가된 경로에 부합하는 결과지만, 이 차이 전체를 순수 네트워크 시간으로 볼 수는 없습니다. `prefill_rpc_ms`에는 대기, tokenization, Prefill과 export가 중복 포함되므로 개별 단계와 합산하지 않습니다.

## OOM과 성능 해석의 구분

수정 전 Router는 HTTP 요청 메타데이터에 KV 본문이 남는 문제로 두 번째 반복에서 1 GiB 상한을 초과했습니다. [안정성 분석](stability.md)에 원인과 수정 전후 검증을 기록했습니다. 주 성능 표는 오류 없이 완료된 첫 반복의 2,560개 요청만 사용합니다.

현재 코드의 동시 전송 수 제한과 실패, 취소 경로 보강은 [Router 메모리 검증](../router-memory-20261001/summary.md)에 별도로 기록합니다.

기존 본문 수명 수정 후 별도 GPU 검사에서도 입력 704, 출력 256, 동시성 8의 처리량은 A 66.77, D 35.26 tok/s였습니다. 해당 검사는 총 160개 요청에 오류와 Pod 재시작이 없었습니다. 따라서 OOM을 수정해도 현재 역할 배치의 Decode 병목은 남습니다. 요청 수와 코드가 다르므로 수정 전후 자료를 동일 반복 통계로 합치지는 않습니다.

## 다음 비교에서 바꿀 조건

현재 결과는 SmolLM2-135M, 최대 실제 입력 734토큰, batch 1, continuous batching과 prefix cache 없이 측정한 결과입니다. 큰 모델, 긴 문맥 또는 여러 물리 GPU에서의 최적화된 분리 서빙으로 일반화하지 않습니다. 전체 workload를 완료한 반복은 1회이므로 작은 차이의 재현성도 아직 확인하지 못했습니다.

다음 실험은 한 번에 하나의 조건을 바꿔야 효과를 구분할 수 있습니다.

1. Decode batching 또는 역할별 자원 비율을 바꾸어 Decode 처리 용량을 확보합니다. 현재 50% 한도보다 큰 Decode 비율은 Pod 환경 변수만으로 올릴 수 없으며 MPS 제어 설정과 동일 총자원 비교 조건을 함께 바꿔야 합니다.
2. Context 한도와 KV 메모리를 검증한 뒤 입력 길이를 늘려 Prefill 비중이 충분히 큰 부하를 추가합니다. 현재 704/16도 계산 시간 기준으로 Decode가 더 길었습니다.
3. 상태 전달 방식의 개선은 별도 실험으로 측정합니다. 현재 긴 출력의 약 47% 처리량 감소를 직렬화 최적화만으로 회복할 것으로 예상하기는 어렵습니다.

Router 메모리 제한 보강 후에는 동일한 전체 matrix를 최소 3회 완료해 재검증해야 합니다. 메모리 스트레스 검사는 이 성능 반복 측정을 대체하지 않습니다.
